# Telegram control MVP

Isolated Cloudflare Worker, read-only. No paid generations, publication, repository writes, or automatic deployment. Requires owner approval before live activation.

1. Install Wrangler locally or use Cloudflare dashboard. Deploy from this directory with npx wrangler deploy after reviewing the code.
2. Configure Worker secrets with wrangler secret put (not public variables): TELEGRAM_BOT_TOKEN, TELEGRAM_OWNER_ID (numeric Telegram user ID), TELEGRAM_WEBHOOK_SECRET (random 32+ characters from a secure generator), ROUTERAI_API_KEY (optional), EDITORIAL_PRIVATE_TOKEN (optional, preferably a separate read-only Contents token for the private review repo).
3. GitHub Actions secrets do not automatically become Worker secrets. Never paste tokens into chat, source code, URLs in a browser, or logs.
4. Register the deployed HTTPS /telegram endpoint using Telegram setWebhook with secret_token equal to TELEGRAM_WEBHOOK_SECRET, allowed_updates ["message"]. Use local protected environment variables or a trusted deployment process. Do not enable webhook until owner ID and secret are set. Verify /health, then /start from owner's private chat.
5. Run node --test worker.test.mjs locally. Never rerun paid editorial tests from this bot.

Current limitations: /status reports mode only, /models lists intended models, /expenses is not connected, /articles and /tests list private result directories (not completed article content). No automatic notifications or controls yet. Future commands should use a durable authorization/approval and budget layer, not direct LLM execution. Telegram delivery can duplicate read-only replies on webhook retries.

## Protected executor intake

The Worker exposes `POST /internal/zen-core/intake` only with a separately provisioned 256-bit hexadecimal `ZEN_CORE_INTAKE_SECRET` (Worker secret, never source or URL). It returns only a confirmed, noncancelled, previewed job; emergency pause blocks the read. The intake is explicitly `intents_only` and cannot authorize model calls or releases. `intake_client.py` submits that envelope to the existing `src.editorial_zen_core.Core` from PR85, using the executor's private persistent database, not a CI ephemeral disk. Example for the operator on that trusted host: `PYTHONPATH=/path/to/executor python telegram-control/intake_client.py --db /private/zen-core.sqlite --endpoint https://YOUR-WORKER/internal/zen-core/intake --job agent:JOB-ID`. Provision the same secret on both hosts without logging it. The client prints only an intake receipt; cancellation after export still requires a separate trusted lifecycle protocol. CI checks the exact PR85 commit with synthetic data, not live transport. Do not deploy or enable real execution until secret provisioning, persistent executor hosting, shared production spend reconciliation, commercial image rights, and end-to-end authorization are verified. The JS finance simulator remains strictly isolated; the Python Core is the intended ledger, not a second competing spending authorization.

## Owner memory (ZEN CORE)

The Settings page includes a persistent, owner-confirmed editorial memory (`agent:memory`). Up to eight notes, 240 characters each, categorized by style, editorial rules, illustrations or workflow. The chat includes these notes as data in the cost-estimated Qwen request. No note changes permissions, budget, schedule, production or RSS. The model cannot write this memory. Saves use a revision check and an explicit confirmation; the audit record stores only revision and note count. Removing a note removes it from current memory, not from already transmitted provider requests. Never store credentials or personal data. Until deployment, all tests remain offline.

## Executor report notifications

The existing owner notification opt-in also covers validated executor receipt transitions: passed/failed/blocked stages, first observed unsettled charge, and exhausted daily main or reserve budget. Notifications are informational, explicitly marked test-mode. Alerts can still arrive while the local emergency gate is stopped; they never resume work. A persistent send claim prevents duplicate delivery of a receipt, including concurrent requests. Ambiguous Telegram outcomes are recorded as unconfirmed and not automatically retried. Notifications are grouped (up to 15 lines plus an additional event count). The full receipt remains in the job. Live Telegram delivery requires deployment and existing owner opt-in. A crash between receipt persistence and notification claim may omit a push; it does not lose the recorded receipt or permit paid work.

## Self-diagnostics

`diagnostics.mjs` provides deterministic read-only observations of local scheduler state, confirmed job previews, executor reports, budget policy and recent chat receipts. The authenticated diagnostics view also reads main-branch configuration. Stale reports are identified explicitly, and errors indicate observed stage status, not a guessed root cause. The Qwen chat receives at most six local diagnostic codes and scopes within its existing request estimate. The UI shows severity and suggested safe next action. This module never retries a paid request, changes limits, clears emergency pause, starts the scheduler, or enables RSS. Diagnostics are computed when the owner opens/refreshes the view or asks the agent; periodic watchdog checks and automatic recovery are not yet connected. Only the latest 40 jobs and 30 chat receipts are examined.

## Safe automatic recovery

The internal Worker scheduled handler invokes a local dry-run watchdog. It only re-arms a missing or more than five-minute-overdue timer when the owner has already enabled the schedule, emergency pause is off, future slots exist and a persisted cursor is valid and no older than two days. Recovery preserves that cursor, uses an atomic storage transaction and a five-minute cooldown, and records the action in the operational journal. Existing deterministic scheduler IDs prevent duplicate dry-run intents. The watchdog never calls providers, retries charges, unpauses a schedule or authorizes publication. It is not exposed through the public Mini App API. Cloudflare Cron Trigger `*/5 * * * *` must be configured explicitly after approved deployment; no trigger has been activated in this branch. The live executor's recovery protocol remains separate. The deployment module manifest now includes all new Worker imports; the optional intake secret is provisioned only through the environment. No live deployment was performed.

Interrupted owner chat: a persistent single-flight charge hold is recorded before each new paid request. A verified receipt settles the original reservation and clears the hold; timeout, unverified model or cost, and overrun preserve it across Moscow midnight. A watchdog quarantines pending requests older than five minutes without sending a replacement. This applies to new requests using the hold schema; older historical pending entries require separate reconciliation. No automatic clearing of an unknown charge is provided. A trusted provider reconciliation path must be implemented before production use. The local watchdog and paid-chat recovery do not resume real article generation.

## Remote executor control gate

`/internal/zen-core/control` is a dedicated bearer-authenticated, per-job, read-only observation. The executor checks it before opening the provider catalogue, at stage boundaries and immediately before a new paid dispatch. Missing, cancelled, stopped, mode-mismatched, stale (>30 seconds) or unavailable control blocks progress. A global mode change freezes incompatible previously confirmed jobs rather than silently changing their mode. The Worker currently always reports executionEnabled=false; no control observation can unlock production. A future live deployment needs `ZEN_CORE_CONTROL_ENDPOINT` and the dedicated intake secret on the trusted host. An in-flight request cannot be revoked. A stop between reservation and dispatch can conservatively leave an unsettled reservation requiring reconciliation. Cached response settlement may still finish without a new model call. No automatic resend, no live transport test, and no publication or RSS activation.

## Automatic intake polling

Confirmed agent orders and enabled schedule jobs in assisted/autonomous mode receive a dry-run preview atomically at creation; manual mode retains a separate preview confirmation. `/internal/zen-core/queue` returns only IDs of confirmed, unacknowledged, mode-compatible jobs, in bounded index pages (20 entries, continuation cursor), excluding cancellation, emergency pause, cinema and paused scheduled jobs. Each ID is revalidated through the existing intake endpoint before cloud submission. `PYTHONPATH=. python telegram-control/intake_client.py --endpoint https://YOUR-WORKER/internal/zen-core/intake --queue` processes up to ten pages per cycle; `--cursor` continues a bounded scan. An operator-managed runner must repeat scans and retain the continuation cursor until the end, then restart from the beginning. If a receipt is lost, the same stable ID is safely submitted again; cloud checkpoints prevent duplicates. No paid requests, execution, deployment or RSS are enabled. A scheduled host and dedicated secret are still required. A cancellation racing with submission can leave an inert intent in the private ledger, but the separate live control check prevents further operations.

## Mode transitions for existing jobs

The owner-confirmed global mode selection now records a monotonically increasing mode revision. Existing confirmed jobs retain their original intent and IDs. The queue redelivers them with a separate mode transition until the private cloud ledger acknowledges the matching revision. `job_modes` is an additive table; `apply_mode` updates only that table and invalidates approvals for unfinished human boundaries. Passed stages, accepted image slots, stored responses and spend are unchanged. Stale revisions and conflicting same-revision changes fail closed. Running sessions pin the effective revision; a later mode change blocks their next new provider call even when the selected mode cycles back. Unconfirmed jobs are not promoted, cancelled jobs are not resumed, and scheduled jobs remain paused until the owner re-enables their schedule. Until receipt synchronization and the separate execution gate succeed, no further paid work can start. This supersedes the older frozen-mode-only behavior. Live transport and production are not enabled.

## Production rolling budget and reporting

The private executor now enforces a 9000 RUB rolling 30 Moscow-calendar-day ceiling inclusive of main and reserve reservations. The daily policy remains 300 RUB plus 50 RUB exclusively for eligible started-article completion. The rolling ceiling is a conservative interpretation of the previous 9000 RUB planning reference. Reserved amounts count before settlement; unknown charges remain blocked across day boundaries. Owner chat remains a distinct 10 RUB/day lane and is not part of this production ceiling. A shared account-wide balance/charge gate is still required before concurrent live use of both lanes. Validated receipts project the latest observed budget to Telegram, explicitly dated and stale after five minutes or on day rollover; a receipt is not a current provider balance. A mismatch of the local owner daily plan with the executor configuration blocks control, not silently raising the actual limit. No real charges, deployment or launch flags changed.

## Account-wide payment serialization

The owner chat hold and production hold share a single Durable Object transaction boundary. Production claims the hold before reserving and dispatching a new paid operation; it rereads credits after claiming, then closes only after the cloud ledger confirms settlement. The chat transaction refuses a production hold, and rechecks provider credits and owner control before dispatch. Holds do not expire at midnight or by timeout. A lost closure receipt can be retried after replaying the saved response and idempotent settlement, with no new model request. Ambiguous claims, missing responses, or uncertain storage updates stop the lane; do not clear them automatically. A confirmed insufficient-balance operation may be closed as not_sent but its operation ID is not reused. This is a cross-lane serialization gate, not a new combined monetary cap. Chat and production retain their separate limits. The actual authenticated production claim endpoint still refuses every claim because the execution gate is closed. Before activation, reconcile historical cloud charges and Worker holds, provide a trusted operator recovery path for orphaned holds, verify the same account and exclusive use of keys by these guarded paths, and test live transport. Historical saved responses predating this gate require migration/reconciliation. Do not bypass the gate by running legacy evaluation scripts with the same key. No model or deployment calls were made.
