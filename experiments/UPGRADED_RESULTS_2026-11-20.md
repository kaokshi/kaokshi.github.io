## Что улучшено

### CLIP: поиск спорных изображений

- `experiments/clip_caption_review.py` поддерживает **любой из трёх каналов**, если для каждой фотографии заранее записано точное английское описание в `experiments/visual_prompt_index.json` по slug. Текст и фото без индекса **не подставляются наугад**.
- Испытывается CPU модель `ViT-B-32/laion2b_s34b_b79k`, извлекаются эмбеддинги 8 фото из существующей статьи «Шоу Трумана» и 8 редакторских подписей плюс 3 контрольных неуместных описания.
- [Первый успешный полный тест восьми фото](https://github.com/kaokshi/kaokshi.github.io/actions/runs/44684667733): **6 из 8 подписей оказались первыми по сходству**, **2 из 8 получили флаг проверки редактором**: `01_seahaven_site.jpg` (подпись «Сихэвен, мир Трумана») и `06_christof_site.jpg` (подпись «Кристоф — создатель шоу»). CLIP дал разницу с лучшей другой подписью -0,0064 и -0,0163 соответственно. Это слабые и близкие значения, поэтому **не считать ни одно изображение ошибочным без визуальной проверки**. [Повторный успешный тест с вынесением описаний в индекс](https://github.com/kaokshi/kaokshi.github.io/actions/runs/44685085191) тоже показал **6/8 и 2/8**, а два автономных регрессионных теста завершились успешно.
- Отчёт указывает исходный файл, английское описание, топ-3 сравнений, оценку и разницу с другими описаниями. Ни одна оценка не доказывает, что кадр снят в нужном фильме, соответствует сюжету, или лицензирован. **Никаких замен кадров автоматически.**

### reviewdog: реальные замечания, а не фиктивный тест

- `experiments/reviewdog_editorial.py` формирует отдельные *.md с абзацами трёх существующих статей и диагностирует отдельные длинные предложения от 24 слов, а также ограниченный набор возможных редакционных штампов.
- По результатам [теста GitHub Actions](https://github.com/kaokshi/kaokshi.github.io/actions/runs/44684747403) **две редакторские подсказки** были найдены в кино-статье; они не являются доказанными ошибками.
- Привязка к строкам сохранена в `reviewdog/diagnostics.json` и `diagnostics.txt`, `reviewdog` успешно принял их с `reporter=local`. Реальные PR-комментарии в GitHub **ещё не протестированы**, и права `pull-requests:write` не включены.
- Исходные JSON-файлы статей и флаги выпуска не меняются.

### Playwright: безопасный прототип согласования

- `experiments/approval_preview.html` и `experiments/remaining_smoke.py Playwright` проверяют **три канала**, а не только форму ввода.
- [Успешный тест Chrome на GitHub runner](https://github.com/kaokshi/kaokshi.github.io/actions/runs/44685206721): **3 из 3** каналов, цикл `вернуть на исправление → указать замечание → редакторски согласовать`; отсутствие текста и замечания блокируется. Во всех состояниях `publication_authorized=false`.
- Для скорости используется предустановленный Chrome GitHub runner. Реальный веб-интерфейс Дзена, ZeroGPT, авторизация и публикация не затрагивались.

### n8n и changedetection.io

- Предыдущие эксперименты подтвердили только работоспособность временных Docker-сервисов; это **не** действующая оркестрация и **не** мониторинг изменений в сети.
- В новой версии они вынесены из частого PR-CI в отдельные ручные тесты, чтобы не тратить бесплатные минуты и Docker-трафик. Для постоянной работы им нужен поддерживаемый сервер.
- **Решение:** пока не внедрять. GitHub Actions и две пользовательские Automations уже выполняют нужные расписания. При появлении конкретного внешнего события выбрать систему мониторинга отдельно.

### peter-evans/create-pull-request

- Остаётся кандидатом: рабочая форма согласования в GitHub уже реализована через обычные черновики PR, включая этот PR #2, без обязательного автоматического предоставления write-токена.
- Сам Action не тестировался на создание PR и не добавлен в постоянный режим, чтобы избежать создания публичных предложений изменений без отдельной проверки разрешений.

## Условия перед переносом в основную систему

1. Повторный тест CLIP с внешним индексом, трёхканальный Playwright и реальный reviewdog локально выполнены успешно. Перед включением в постоянную редакцию проверить полные артефакты и утвердить критерии тревожных совпадений.
2. Сделать способ редакторского выбора: пропустить/проверить/исправить каждую подсказку; правки должны быть отдельным диффом, не замещать первичную статью.
3. Включать CLIP только как **необязательный диагностический шаг** по событию/ручному запросу, а не каждый раз при сборке сайта: вес модели и CPU расходуют минуты.
4. Реальные GitHub PR-аннотации подключать только после отдельного разрешения на `pull-requests:write`.
5. Все внешние сайты, кадры и авторские права перепроверять отдельно; никаких обещаний 100% достоверности.

**Ни один из модулей не включает публикацию, не редактирует черновики и не меняет утверждённый регламент.**
